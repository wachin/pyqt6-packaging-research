# Packaging Study: Pyzo

## 1. Executive Summary

Pyzo is a pure-Python, cross-platform scientific Python IDE. This repository's **current release binaries are made with PyInstaller**, not Nuitka. The maintained freezer deliberately creates **one-directory (`--onedir`)** bundles, then wraps them as follows:

```text
Python source + selected Qt binding
  └─ PyInstaller one-directory bundle
     ├─ Windows: portable ZIP + 64-bit Inno Setup EXE installer
     ├─ Linux: portable ZIP + portable tar.gz
     └─ macOS: .app + ZIP + DMG
                         └─ Developer-ID signing, hardened runtime,
                            timestamp, notarization, stapling (CI only)
```

There is **no AppImage, no Debian package, no Nuitka, no Windows Authenticode signing, no checksum manifest, no SBOM, and no artifact attestation** in the tracked implementation. Linux release binaries are deliberately built on Ubuntu 22.04, but are ordinary PyInstaller directory archives rather than distribution-native packages. The README explicitly recommends source execution on Linux because of possible Qt library incompatibilities ([README.md](README.md#L30)).

This is a useful mature case study, especially for explicit PyInstaller inclusion/exclusion control, frozen-app smoke tests, CI release orchestration, and macOS notarization. It is not a blueprint for a new PyQt6-only application: Pyzo must preserve a multi-binding and legacy-32-bit compatibility matrix, and it bundles source deliberately to enable its plug-in-oriented IDE behavior.

**Evidence convention.** “Actual” means directly supported by the checked-out source at commit `7f9679625c8bf028a3f796e6cba6f6d6c18dd063`; paths and line numbers refer to that checkout. “Not verified from the available evidence” is used where a conclusion would otherwise be speculative. Public releases are created by `github-actions`; the current GitHub Releases page shows v4.22.0 with ten assets and an autogenerated-binaries note ([releases](https://github.com/pyzo/pyzo/releases)).

## 2. Project Architecture

- **Name and purpose:** Pyzo, “The Interactive editor for scientific Python”; an IDE focused on interactivity and introspection ([README.md](README.md#L1), [README.md](README.md#L11)).
- **Languages:** primarily Python 3; shell/kernel code intentionally retains Python 2.7 compatibility. The Inno Setup installer is `.iss`; GitHub Actions uses YAML; desktop metadata is XML and `.desktop` ([CONTRIBUTING.md](CONTRIBUTING.md#L86)).
- **IDE Python requirement:** `>=3.6` in metadata and runtime check ([pyproject.toml](pyproject.toml#L14), [pyzo/__init__.py](pyzo/__init__.py#L41)). Current release jobs use Python 3.14 except Linux/Win32, which use Python 3.9 ([.github/workflows/cd.yml](.github/workflows/cd.yml#L20), [.github/workflows/cd.yml](.github/workflows/cd.yml#L220)).
- **Kernel Python:** chosen by the user and may be Python 2.7+, PyPy, or a different interpreter; it is not the frozen IDE runtime ([CONTRIBUTING.md](CONTRIBUTING.md#L88)).
- **Qt binding:** source dynamically supports PySide6, PyQt6, PySide2, and PyQt5, in that preference order; `QT_API` can select one ([pyzo/qt/__init__.py](pyzo/qt/__init__.py#L4)). Release builds select PySide6 for Win64/macOS and PyQt5 for Win32/Linux ([.github/workflows/cd.yml](.github/workflows/cd.yml#L51), [.github/workflows/cd.yml](.github/workflows/cd.yml#L216)). It does not use QtPy.
- **Qt version requirement:** no pinned project-level Qt version or minimum is declared. The binding wheel determines the Qt runtime. CI tests several bindings/Python versions, rather than declaring a single PyQt6 support range ([.github/workflows/ci.yml](.github/workflows/ci.yml#L41)). Exact Qt versions contained in released artifacts are **not verified from the available evidence** because dependencies are installed with `-U` and no lock file is present.
- **Entry points:** source launcher is `pyzolauncher.py`; installed GUI console entry point is `pyzo = "pyzo:start"` ([README.md](README.md#L49), [pyproject.toml](pyproject.toml#L36)); the frozen executable starts from `freeze/boot.py` ([freeze/pyzo_freeze.py](freeze/pyzo_freeze.py#L25)).
- **Layout:** application package `pyzo/`; kernel `pyzo/pyzokernel/`; messaging `pyzo/yoton/`; GUI compatibility layer `pyzo/qt/`; application assets under `pyzo/resources/`; freezer/release utilities under `freeze/`; CI/CD under `.github/workflows/`; basic tests in `tests/`.
- **Dependency/build metadata:** Flit (`flit_core >=3.2,<4`) builds source distributions/wheels; runtime `dependencies = []` because users choose a Qt binding ([pyproject.toml](pyproject.toml#L24), [pyproject.toml](pyproject.toml#L42)). Thus PyPI packaging and desktop-binary freezing are separate systems.

## 3. Packaging Overview

### Actual packaging map

```text
tag vX.Y.Z
  └─ CD workflow (.github/workflows/cd.yml)
     ├─ Windows x64: Python 3.14 + PySide6 + PyInstaller
     │  └─ freeze/pyzo_freeze.py -> freeze/dist/pyzo/
     │     └─ freeze/pyzo_package.py -> ZIP + Inno Setup EXE
     ├─ Windows x86: Python 3.9 + PyQt5 + PyInstaller
     │  └─ onedir -> ZIP only (installer intentionally skipped)
     ├─ Linux x86_64: Ubuntu 22.04 + Python 3.9 + PyQt5 + PyInstaller
     │  └─ onedir -> ZIP + tar.gz
     ├─ macOS x86_64 and arm64: Python 3.14 + PySide6 + PyInstaller
     │  └─ pyzo.app -> codesign -> notarytool -> staple -> ZIP + DMG
     └─ publish job -> GitHub Release assets
```

`freeze/pyzo_freeze.py` generates a temporary `freeze/pyzo.spec` with PyInstaller’s `makespec`, alters it only on macOS to insert the Pyzo version, then runs PyInstaller on that spec ([freeze/pyzo_freeze.py](freeze/pyzo_freeze.py#L232)). The generated spec is not tracked, therefore it is build output rather than a hand-maintained configuration file. `freeze/pyzo_package.py` gives archives names such as `pyzo-<version>-win64.zip` ([freeze/pyzo_package.py](freeze/pyzo_package.py#L14)).

### Legacy / non-release infrastructure

- The commented `setup.py`-era AppStream installation logic in `pyproject.toml` is historical, not active ([pyproject.toml](pyproject.toml#L50)).
- The repository history shows the older `freeze/freezeScript.py` was deleted during the 2021 refactor; do not treat it as current infrastructure.
- `pyzo/resources/org.pyzo.Pyzo.desktop` is a source-install template, not a Debian/AppImage packaging recipe; it instructs users to copy/customize it ([pyzo/resources/org.pyzo.Pyzo.desktop](pyzo/resources/org.pyzo.Pyzo.desktop#L8)).
- The CD artifact glob includes `*.msi`, but no WiX/MSI build input or command exists. This is likely a harmless stale glob; no MSI production is verified ([.github/workflows/cd.yml](.github/workflows/cd.yml#L40)).

## 4. Windows

### Actual pipeline

Win64 uses `windows-latest`, Python 3.14, latest PySide6/PyInstaller, and `freeze/frozen_libs.txt`; it freezes, packages, starts the frozen EXE in test mode, validates the log, uploads ZIP/EXE/MSI matching files, and tag builds publish them ([.github/workflows/cd.yml](.github/workflows/cd.yml#L15)). Win32 uses Python 3.9/x86 and PyQt5, producing a ZIP only ([.github/workflows/cd.yml](.github/workflows/cd.yml#L46)).

The portable output is `freeze/dist/pyzo/` with `pyzo.exe` and PyInstaller’s `_internal` content. The Inno installer includes all files recursively, installs by default under `{pf}\pyzo`, and offers desktop/start-menu shortcuts plus optional `.py` association ([freeze/installerBuilderScript.iss](freeze/installerBuilderScript.iss#L14), [freeze/installerBuilderScript.iss](freeze/installerBuilderScript.iss#L37)). `PrivilegesRequired = none` makes the installer per-user by default; selecting the file association may require elevation ([freeze/installerBuilderScript.iss](freeze/installerBuilderScript.iss#L23)). It uses LZMA solid compression, which applies to the installer payload, not PyInstaller’s `--onefile` mode ([freeze/installerBuilderScript.iss](freeze/installerBuilderScript.iss#L34)).

### Installer and signing answers

- **Installer technology:** Inno Setup 5 or 6, invoked through `ISCC.exe`; only 64-bit gets an installer because the script comments that the 32-bit installer is broken ([freeze/pyzo_package.py](freeze/pyzo_package.py#L69)).
- **Portable and installer:** Win64 intends to produce both ZIP and EXE installer; Win32 produces portable ZIP only.
- **Onefile/onedir/windowed:** explicitly `--onedir`; Windows adds `--windowed`, equivalent to no console window ([freeze/pyzo_freeze.py](freeze/pyzo_freeze.py#L247)). No `--onefile` is used.
- **Windows executable signing:** no `signtool`, Authenticode certificate, timestamp service, signing action, or signing command is present. **Not verified from the available evidence** whether a release asset was manually signed outside this repository; the tracked automated pipeline does not sign it.
- **Windows installer signing:** likewise no evidence. The installer is built after freezing and no signing follows. Do not infer that its icon/publisher strings are an Authenticode identity.
- **EXE metadata/manifest/UAC:** a PyInstaller icon is supplied, and Inno has `AppPublisher`, URL, and version display strings ([freeze/pyzo_freeze.py](freeze/pyzo_freeze.py#L256), [freeze/installerBuilderScript.iss](freeze/installerBuilderScript.iss#L4)). No PyInstaller version-resource file, custom PE manifest, explicit UAC manifest, or custom bootloader is tracked. `PrivilegesRequired=none` concerns installer elevation, not the application executable.

## 5. PyInstaller

### Effective specification, line by line

There is no committed `.spec`; the script is the authoritative spec generator.

- Lines 21–29 set name, selected binding, entry script, output directory, and platform icon.
- Lines 52–121 enumerate nearly all standard-library importable modules while excluding tests, Tk, idle, `distutils`, etc. This deliberately supports Pyzo’s extensibility more broadly than PyInstaller’s static import analysis.
- Lines 124–126 define other bindings and remove the selected one; lines 140–154 add almost all stdlib, `dialite`, and exactly `QtCore`, `QtGui`, `QtWidgets`, and `QtPrintSupport` as hidden imports ([freeze/pyzo_freeze.py](freeze/pyzo_freeze.py#L140)).
- Lines 157–200 exclude Tk, every non-selected binding, and many unused Qt modules. The stated result is about 120 MB instead of ~300 MB for PySide because PySide otherwise collects more Qt modules ([freeze/pyzo_freeze.py](freeze/pyzo_freeze.py#L163)). The exclusions include `QtNetwork`, `QtSvg`, `QtDBus`, multimedia, QML/Quick, etc.; therefore network/TLS, SVG, image-feature, and other plugin needs should not be assumed to be included.
- Lines 202–217 add `_settings` and the full `pyzo` source tree as data. On macOS source is copied after freezing due to issue #830; elsewhere PyInstaller copies it.
- Lines 241–264 make a one-directory build and append one hidden import/exclusion/add-data flag per discovered item. Windows/macOS use `--windowed`; macOS additionally supplies `.icns` and `org.pyzo.app` bundle id.
- Lines 270–287 write the generated spec, inject `version=` into macOS `BUNDLE`, then run `PyInstaller --clean --distpath ... specfile`.
- Lines 297–307 copy source under `.app/Contents/Resources/source` on macOS.

The standard generated PyInstaller spec therefore contains the usual `Analysis`, `PYZ`, `EXE`, `COLLECT`, and macOS `BUNDLE` stages; exact generated syntax varies by installed PyInstaller version and is **not committed for inspection**. PyInstaller’s official docs describe one-folder as the default and `--windowed` as the GUI/no-console option ([PyInstaller usage](https://pyinstaller.org/en/stable/usage.html)).

### Qt, data, and runtime behavior

PyInstaller’s binding hooks collect the selected binding’s needed Qt binaries/plugins, subject to the explicit module selection above. The project does not maintain hooks, runtime hooks, manual `--add-binary` lists, plugin paths, or `qt.conf`. Consequently the precise plugin directory contents (platforms, imageformats, iconengines, styles, TLS) in a particular release are **not verified from repository files**; inspect an emitted `_internal` directory or PyInstaller build warnings to prove them.

The frozen boot program uses `sys._MEIPASS`, adding either `_MEIPASS/source` or, on macOS, `../Resources/source` to `sys.path` and a custom meta-path importer ([freeze/boot.py](freeze/boot.py#L86)). This makes the copied source/resources work in a frozen onedir bundle. It is intentional source shipping, not Qt’s compiled `.qrc` resource system.

UPX is not installed, enabled, disabled, or mentioned in the repository. PyInstaller only invokes UPX if it can find it; absence of a `--noupx` flag is not evidence that UPX actually ran. Therefore **UPX use is not verified from the available evidence**. For a fresh release pipeline, set `--noupx` or ensure UPX is absent if the policy is to avoid it, making the choice auditable. PyInstaller documents both automatic UPX use when available and `--noupx` ([PyInstaller usage](https://pyinstaller.org/en/stable/usage.html)).

## 6. Nuitka

Nuitka does not occur in current files or relevant history search results. PyInstaller was apparently selected because Pyzo needs a cross-platform freezer that can bundle a selected Qt binding while retaining broad Python source importability; the script predates today’s release workflow and exposes PyInstaller’s well-understood hidden-import/exclude controls. This is an inference from implementation, not an explicit maintainer rationale.

For a new PyQt6 app, Nuitka is a reasonable alternative, not a drop-in “better” answer:

| Topic | PyInstaller | Nuitka |
| --- | --- | --- |
| Build model | bundles CPython bytecode/interpreter and dependencies | compiles Python modules to C/C++-backed binaries, then bundles runtime |
| Build speed/toolchain | usually faster and no C compiler normally required | usually slower; needs a supported C/C++ compiler/toolchain |
| Qt support | mature hooks, but inspect collection output | use its PyQt6/PySide6 plug-in and explicitly select needed Qt plugins |
| Modes | onedir/default or onefile | standalone/onefile, and macOS app-bundle modes |
| Debugging | transparent directory tree and PyInstaller diagnostics | compiler-stage plus package-inclusion diagnostics |
| Startup | onedir avoids extraction; onefile extracts | standalone avoids onefile extraction; onefile has extraction/launch overhead |
| AV reputation | no guarantee; common bootloader/packing patterns may attract heuristic detections | no guarantee; different compiled output may produce different detections |

Nuitka’s official manual documents Qt plugins and standalone/onefile choices ([Nuitka user manual](https://nuitka.net/user-documentation/user-manual.html)). Evaluate it with release candidates on each platform and retain the tool with the most reliable application behavior, maintainability, and signing pipeline—not merely a single VirusTotal score.

## 7. Antivirus / VirusTotal Considerations

### Evidence-backed facts

- Pyzo uses PyInstaller **onedir**, not a self-extracting onefile executable ([freeze/pyzo_freeze.py](freeze/pyzo_freeze.py#L247)). This avoids onefile’s runtime extraction behavior, but the repository does not claim it improves AV results.
- It uses a stable application name and icon, plus installer publisher/version display text ([freeze/installerBuilderScript.iss](freeze/installerBuilderScript.iss#L4)). These are professional metadata, not proof of reputation effects.
- It does not show UPX configuration, a custom/recompiled bootloader, code obfuscation, VirusTotal scanning, antivirus submissions, deterministic builds, Windows signing, hashes, or provenance attestations.
- The ZIP/installer payload is compressed (ZIP deflate and Inno LZMA), but this is ordinary archival/installer compression. No causal link to detection rate is established here.

### Practical conclusion

No “magic” anti-false-positive technique is evidenced. Onedir may be operationally preferable because it avoids onefile extraction, but it does not guarantee fewer detections. A signed, timestamped application/installer from a consistent publisher, clear version metadata, public source/release notes, hashes/provenance, current dependencies, and submitting genuine false positives to the detecting vendor are legitimate trust/reputation practices. They can reduce friction but cannot guarantee zero VirusTotal detections, SmartScreen reputation, or vendor classification. Do not use obfuscation, evasion, altered bootloaders merely to evade scanners, or antivirus disabling.

## 8. Windows Installer

Inno Setup is a sensible small-project installer for a portable onedir tree: it supports shortcuts, uninstall, optional association, compression, and non-admin default installation. Pyzo’s `.iss` is project-specific in several ways: hard-coded product name/id, `C:\Program Files` default, bitmap locations inside PyInstaller’s `_internal/source` layout, `.py` association, and its 32-bit-installer limitation. Reuse the concept, not those paths/identity values blindly.

For a new open-source PyQt6 application, choose a portable ZIP plus a signed Inno Setup installer unless you have an enterprise requirement for MSI/MSIX/WiX. Sign **all user-facing PE files that execute** where feasible, build the installer from signed files, then sign/timestamp the installer too. Publish SHA-256 sidecars and release provenance. That sequence is absent from Pyzo Windows automation.

## 9. Windows Code Signing

Actual sequence: `freeze -> package (ZIP, Inno EXE) -> test -> artifact/release`. There is no tracked signing insertion point. Recommended sequence for another project is:

```text

          -> compile installer -> Authenticode-sign/timestamp installer
          -> SHA-256 + provenance -> GitHub Release
```

## 10. Linux

Actual Linux output is an x86_64 PyInstaller onedir tree archived as both `pyzo-<version>-linux_<machine>.zip` and `.tar.gz` ([freeze/pyzo_package.py](freeze/pyzo_package.py#L39)). The job runs Ubuntu 22.04/Python 3.9/PyQt5 and installs XCB/DBus dependencies before freezing/testing ([.github/workflows/cd.yml](.github/workflows/cd.yml#L211)). It opens the frozen app under `xvfb-run`, then checks its success log ([.github/workflows/cd.yml](.github/workflows/cd.yml#L236)).

The “somewhat older Ubuntu” comment is a portability attempt: native binaries compiled against a newer glibc can require symbols unavailable on older distributions. Building on a lower supported glibc baseline generally broadens compatibility; it never guarantees compatibility because bundled/host graphics, C++ ABI, drivers, and Qt/XCB dependencies still matter. The README’s warning about Qt incompatibility is consistent with this limitation ([README.md](README.md#L30)). No container, explicit glibc audit, `patchelf`, RPATH policy, or cross-distribution VM test exists.

## 11. AppImage

Pyzo does **not** create or publish an AppImage in the tracked pipeline. No `AppDir`, `AppRun`, `appimagetool`, `linuxdeploy`, `linuxdeploy-plugin-qt`, `appimage-builder`, or AppImage CI test was found. It therefore does not provide evidence for how its Qt/Python runtime, plugins, RPATH, desktop file, icon, or AppStream metadata would work inside an AppImage.

Do not mislabel its `.tar.gz` as AppImage: users extract and run the directory tree; it has none of AppImage’s single-file mount/launcher behavior. AppImage remains a separate packaging design for a new project and is outlined in the companion tutorial.

## 13. macOS

PyInstaller uses `--windowed`, `.icns`, and bundle identifier `org.pyzo.app`, which creates `freeze/dist/pyzo.app` ([freeze/pyzo_freeze.py](freeze/pyzo_freeze.py#L259)). The generated spec is modified to put Pyzo’s version in the BUNDLE ([freeze/pyzo_freeze.py](freeze/pyzo_freeze.py#L276)). The repository intentionally puts Pyzo source in `Contents/Resources/source`; boot code detects PyInstaller macOS paths and imports it there ([freeze/boot.py](freeze/boot.py#L87)). PyInstaller collects the Python runtime, selected PySide6/Qt libraries/plugins, and its normal bundle internals; no maintained `Info.plist` template, entitlements file, manually defined framework list, or Qt config file is tracked.

`pyzo_package.py` creates a ZIP of the `.app` and a read-only compressed UDZO/HFSX DMG with `hdiutil create -srcfolder pyzo.app` ([freeze/pyzo_package.py](freeze/pyzo_package.py#L98)). It has no drag-to-Applications layout customization. Separate Intel (`macos-15-intel`) and Apple Silicon (`macos-latest`) artifacts are built; Intel is described as usable through Rosetta on modern Macs ([.github/workflows/cd.yml](.github/workflows/cd.yml#L80)).

## 14. macOS Code Signing

Both macOS jobs import a base64-encoded `.p12` certificate into a temporary CI keychain, then run:

```bash
codesign --force -s "$MACOS_CERTIFICATE_NAME" --all-architectures \
  --timestamp --deep --options runtime freeze/dist/pyzo.app -v
```

([.github/workflows/cd.yml](.github/workflows/cd.yml#L98); mirrored for arm64 at [.github/workflows/cd.yml](.github/workflows/cd.yml#L164)). This signs the application bundle with hardened runtime and a secure timestamp. `--deep` asks codesign to sign nested code; for a newly designed pipeline, explicitly signing/validating nested frameworks, plugins, helpers, then the outer app is easier to audit than relying only on `--deep`.

Secrets (names only): `PROD_MACOS_CERTIFICATE` (base64 P12), `PROD_MACOS_CERTIFICATE_PWD`, `PROD_MACOS_CERTIFICATE_NAME` (signing identity), and `PROD_MACOS_CI_KEYCHAIN_PWD` (temporary keychain). The actual certificate class/subject is not exposed; it is reasonable to infer intended Developer ID use from the notary workflow, but certificate type is **not verified from the available evidence**. Apple requires a Developer ID signing identity, hardened runtime, and secure timestamp for normal direct-distribution notarization ([Apple notarization documentation](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution?changes=_9)). This requires membership/credentials in the Apple Developer Program; PyInstaller and `hdiutil` alone do not.

## 15. macOS Notarization

Actual sequence:

```text
PyInstaller .app
  -> codesign --options runtime --timestamp --deep
  -> ditto -c -k --keepParent pyzo.app notarization.zip
  -> xcrun notarytool submit ... --wait
  -> xcrun stapler staple pyzo.app
  -> ZIP and DMG packaging
```

([.github/workflows/cd.yml](.github/workflows/cd.yml#L113)). Credentials are stored as a `notarytool-profile` in the temporary keychain. Secrets: `PROD_MACOS_NOTARIZATION_APPLE_ID`, `PROD_MACOS_NOTARIZATION_TEAM_ID`, and `PROD_MACOS_NOTARIZATION_PWD` (an app-specific password or other credential accepted by that command). The pipeline staples the **app**, then creates the DMG. It does not separately codesign or notarize/staple the DMG, and no `spctl`/`codesign --verify` validation command is shown. Whether Apple accepts the resulting DMG precisely as users receive it is supported indirectly by release operation but not independently verified here. Apple documents `notarytool` submission and stapling as the supported command-line pattern ([Apple documentation](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution?changes=_9)).

## 16. GitHub Actions

### CI

`ci.yml` triggers on main pushes/PRs and manual dispatch. It runs Ruff, then a non-fail-fast OS/Python/binding matrix spanning Windows, Ubuntu, and macOS; PyQt6 is tested at Python 3.11 and multiple PySide/PyQt variants are covered ([.github/workflows/ci.yml](.github/workflows/ci.yml#L36)). It installs editable Pyzo, runs pytest, starts Pyzo for five-second `--test` smoke runs (Xvfb on Linux), then checks the log.

### CD

`cd.yml` triggers manually, on tags `v*`, and branches `cd`, `bump`, `freeze`; only successful tag builds publish ([.github/workflows/cd.yml](.github/workflows/cd.yml#L5), [.github/workflows/cd.yml](.github/workflows/cd.yml#L248)). Build jobs upload artifacts; `publish` downloads them, creates a GitHub Release with `gh release create --verify-tag`, and uploads ZIP/tar.gz/DMG/EXE/MSI patterns ([.github/workflows/cd.yml](.github/workflows/cd.yml#L267)). `GITHUB_TOKEN` is the only publishing secret and is used for release creation/upload. It has `contents: write`; no cache, pinned dependency lock, checksum, release signature, SBOM, or artifact-attestation step exists.

README accurately says release binaries exist for Windows/Linux/macOS and gives a PyInstaller freeze command ([README.md](README.md#L30), [README.md](README.md#L70)). It does not claim AppImage, Debian, Windows signing, or Windows AV validation, so no direct documentation/implementation contradiction was found. Its Linux source recommendation is materially more cautious than the existence of an archive release and should be retained.

## 17. Resource Handling

Pyzo uses filesystem assets, not Qt `.qrc` resources: `pyzo/resources/` holds PNG/SVG/BMP/ICO/ICNS app/UI icons, images, fonts, themes, `.ssdf` configuration, desktop/AppStream metadata, code examples, TS/QM translations, and tutorial source. The freezer includes the entire `pyzo` tree as `source/pyzo`, so all of those assets are shipped as ordinary files ([freeze/pyzo_freeze.py](freeze/pyzo_freeze.py#L210)). Runtime code resolves them through `pyzo.pyzoDir`, e.g. themes and default configuration ([pyzo/_start.py](pyzo/_start.py#L151)).

This works for PyInstaller because `boot.py` establishes the source directory. The same concept must be translated deliberately for Nuitka, AppImage, a `.deb`, and a macOS bundle; do not copy `sys._MEIPASS` into a non-PyInstaller build. Qt `.qrc` would embed selected immutable assets into the binary, but Pyzo needs a browsable source/resource tree and does not use it.

## 18. PyQt6 / Qt Plugins

Pyzo source supports PyQt6 but release output is not uniformly PyQt6: Win64/macOS use PySide6, while Linux/Win32 use PyQt5. This directly answers a common trap: Pyzo is not a “PyQt6 packaging” example; it is a multi-binding Qt desktop application that selects different bindings per artifact for compatibility.

Only Core/Gui/Widgets/PrintSupport are requested as hidden imports. PyInstaller’s binding hooks provide the concrete Qt libraries/plugins. No hand-maintained include list proves platform, imageformat, iconengine, style, TLS/network, or Qt translation plugin selection. Before copying this approach, inspect a clean output tree and run feature tests that exercise native file dialogs, printing, icons/images, and any network features actually used.

## 19. Translations

Pyzo ships its own compiled `pyzo_*.qm` files beside `.ts` source in `pyzo/resources/translations/`; the full resource directory is included by freezing. `setLanguage()` obtains Qt’s own translations path with `QLibraryInfo`, then installs both `qt_<locale>.qm` and Pyzo’s `pyzo_<locale>.qm` via `QTranslator` ([pyzo/util/_locale.py](pyzo/util/_locale.py#L85)). This is the correct conceptual mechanism for standard Qt dialog strings such as Open/Save/Print: Qt’s `qt_*.qm` must be available in the packaged Qt translation location.

The code tries to load Qt translations, but the repository does not explicitly add their files. Whether PyInstaller’s selected binding hook includes `translations/qt_*.qm` for every release is **not verified from the available evidence**. Test an actual non-English frozen artifact’s standard dialogs. The translation maintenance tool uses PySide6’s Linguist utilities; that does not mean release binaries use PySide6 ([TRANSLATIONS.md](TRANSLATIONS.md#L6)).

## 20. Security and Release Integrity

- **Present:** public source, BSD-2-Clause license, tagged GitHub release automation, `--verify-tag` on release creation, smoke tests, macOS signing/notarization, and public release metadata. GitHub currently displays a verified signature for its latest release tag/commit, but the workflow itself does not enforce tag signing ([releases](https://github.com/pyzo/pyzo/releases)).
- **Absent/not verified:** lock file, dependency hashes, pinned release dependencies, SBOM, SLSA/provenance attestation, release SHA-256 files, binary signing on Windows, Linux package signatures, reproducible-build controls, secret scanning/dependency scanning configuration, and tag-signing policy.
- **Important nuance:** `pip install -U` intentionally takes newest compatible packages at build time, which makes builds less reproducible. Dynamic PyInstaller output and timestamps/compressed archives also prevent a reproducible-build claim.

For a small project, add a reviewed lock/constraints file for release jobs, create SHA-256SUMS, attach an SBOM and GitHub artifact attestations, and publish how users verify each. GitHub says attestations establish provenance/integrity links, not that an artifact is intrinsically safe ([GitHub Docs](https://docs.github.com/en/actions/concepts/security/artifact-attestations)).

## 21. Techniques Worth Reusing

- **[HIGHLY RECOMMENDED]** Per-platform native CI builds and a tag-gated publishing job; PyInstaller is not a cross-compiler.
- **[HIGHLY RECOMMENDED]** Start the frozen application in CI and assert a success log, not merely that packaging exited zero.
- **[HIGHLY RECOMMENDED]** Explicitly include the Qt modules/features used and exclude unused bindings/modules, then validate output size and behavior.
- **[HIGHLY RECOMMENDED]** macOS Developer-ID signing with hardened runtime, secure timestamp, notarization, stapling, and clean-machine testing.
- **[HIGHLY RECOMMENDED]** Build Linux binaries on the oldest supported baseline and state compatibility limits.
- **[USEFUL]** Offer a portable archive alongside an installer.
- **[USEFUL]** Keep desktop metadata, application ID, icons, and version naming consistent across artifacts.
- **[USEFUL]** Use a short-lived CI keychain and secrets only for signing/notarization.

## 22. Techniques Specific to This Project

- **[PROJECT-SPECIFIC]** Copying all Pyzo source into the bundle and installing a `SourceImporter`; it supports Pyzo’s IDE/tool architecture but exposes source and is unnecessary for most apps.
- **[PROJECT-SPECIFIC]** Including almost the whole stdlib to support unknown user-side tooling.
- **[PROJECT-SPECIFIC]** Multi-binding selection and shipping PySide6 on some targets/PyQt5 on others.
- **[PROJECT-SPECIFIC]** Optional `.py` association, Pyzo-specific product IDs/icons, and portable `settings` directory behavior.
- **[LEGACY]** Python 3.9/PyQt5 Win32/Linux release choice; retain only if your own support policy needs it.
- **[LEGACY]** Commented setup.py-era AppStream installation code and obsolete generated/freezer history.

## 23. Problems or Weaknesses Found

- No AppImage or `.deb`, despite Linux being a target; tar.gz is not native desktop integration.
- Linux supports a single aged binding/runtime baseline and README warns about Qt incompatibility.
- Windows assets lack tracked Authenticode signing/timestamping; this is the largest professional-distribution gap and offers no evidence-based AV reputation mitigation.
- No release checksums, locked build dependencies, SBOM, provenance attestations, or stated reproducibility policy.
- Qt translator collection and detailed Qt plugin contents are delegated to PyInstaller hooks without an explicit artifact validation test.
- Inno’s current installer script states the 32-bit installer is broken; CI uploads a stale `*.msi` glob without an MSI builder.
- macOS uses `codesign --deep`; it works as an automation shortcut but explicit nested signing/verification would be more auditable. DMG itself is not separately notarized/stapled in tracked code.

## 24. Recommended Approach for My PyQt6 Projects

Use a PyQt6-only dependency model, a lock/constraints file, and native CI builders. Start with PyInstaller onedir if it reliably collects your app; choose Nuitka standalone after comparative prototypes if its compiled mode materially improves performance/AV outcomes for your app and you accept compiler complexity. Avoid onefile as the default: onedir/standalone is easier to debug, patch, scan, and package in an installer.

On Windows: set version/icon/manifest metadata, avoid UPX unless deliberately tested, Authenticode-sign/timestamp the application and installer, publish SHA-256 and provenance, and check VirusTotal only as a release-quality signal. On Linux: provide a real AppImage for portable distribution plus a distro-dependency `.deb` for Debian/Ubuntu users; build AppImage against an intentionally old glibc baseline. On macOS: make an `.app`, sign all nested code and the bundle with Developer ID/hardened runtime/timestamp, notarize/staple, then ship a DMG or signed ZIP. See [PYQT6_PACKAGING_TUTORIAL.md](PYQT6_PACKAGING_TUTORIAL.md).

## 27. Final Conclusions

1. **Windows:** PyInstaller onedir with `--windowed`; Win64 ZIP plus Inno Setup EXE, Win32 ZIP. No tracked signing, UPX policy, VT check, custom bootloader, or checksum.
2. **Linux:** PyInstaller onedir archives only; no AppImage or Debian package. Runtime is bundled in the archive, while some system XCB/DBus dependencies remain host concerns.
3. **macOS:** PyInstaller `.app`, ZIP/DMG, code signing with hardened runtime/timestamp, notarization, and app stapling. This is the repository’s strongest end-user trust pipeline.
4. **CI/CD:** a good native-platform/tag-release design with runtime smoke tests, but dependency/release integrity controls remain modest.
5. **For a new PyQt6 project:** borrow the platform-specific CI, test, signing/notarization, and explicit bundle policy; add Windows signing, AppImage/.deb strategy, hashes/provenance/SBOM, and a reproducible dependency policy. Treat Nuitka as a measured alternative, not an automatic upgrade.
